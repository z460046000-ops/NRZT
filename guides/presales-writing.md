# 售前方案写作规则

本规则从人工制作的 CallWan 企业增长方案、协同工作台方案中抽取**组织方法**。样本里的数字、功能、案例和承诺不是通用事实；生成任何新方案都须重新核对当前授权材料。

## 按材料选择叙事

- 企业增长/营销：背景与机会 → 目标客户的典型挑战 → 问题对应的业务链路与做法 → 平台支撑 → 实施与服务。能力页应说明从内容、触达到线索与复盘的因果关系，不把功能名排成目录。
- 企业协同/工作台：业务背景 → 客户问题与逐项对应的做法 → 人机协同机制和能力 → 典型落地场景 → 当前阶段与合作边界。产品处于试点或能力建设中时，明确区分已具备、试点中与规划中。
- 章节由材料决定，通常 3—6 章。封面只承载名称、主张、版本等必要信息，目录在后续页面；同一章可以有若干张页面，不为凑页数重复观点。

## 事实与表达

1. 每条挑战都要对应具体做法，并解释该做法如何回应挑战。无法建立对应关系时，分别写成待核实的典型挑战和已确认能力，不硬凑配对。
2. 初次接触客户，只写“典型挑战”“适用场景”，不声称客户已经遇到该问题；深入接触时，客户现状必须来自客户明确提供的资料。
3. 企业能力、数字、客户案例、价格和服务承诺必须由当前产品资料逐字支撑。来自公开搜索的材料只可补充行业背景或典型问题，标记“待核实”，不能替代企业能力依据。
4. 以客户能理解的业务结果和运行机制组织内容。API、组件名和架构术语仅在解释实施边界时出现，不把代码、接口目录或原始材料塞进正文。
5. 资料缺口不等于整稿停止。先交付已核实章节形成可编辑初稿；对缺失章节点名说明，让用户在对话里补充，或选择公开检索。补充后生成新版，旧版保留。完全没有有据正文时拒绝空稿。
6. 每章优先写 2—4 个有信息量的段落、要点或步骤。所有入稿事实保留准确来源与连续原文引文；逐字校验失败时重试该章，仍失败则保留待确认并在对话中说明。

## 交付检查

- 核对背景、挑战、做法、场景和边界的前后关系，以及标题与正文是否一致。
- 未完成章、待核实公开信息和用户补充事实在内部稿中可见；不得把它们伪装成已完成的对外方案。
- JSON、HTML、Markdown、Word 共用同一版本的章节结构；人工编辑后按现有版本机制同步生成。
